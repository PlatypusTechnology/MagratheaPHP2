# 2.4.0 security update

Found on 2026-10-23: four security holes in the admin's database and log tools that the 2.4.0
sweep (items 1–5e) missed. They exist in 2.3.4 as well (the latest tag). 2.4.0 isn't tagged yet
and is in testing, so they're fixed in 2.4.0 before it's released, **on the `version/2.4.0`
branch**. Line numbers refer to `version/2.4.0` at `f61e482`.

## Before starting

`git branch --show-current` must say `version/2.4.0`. Run the baseline suite first
(`php phpunit.phar --bootstrap src/Tests/phpUnitBootstrap.php src/Tests`), expected
**363 tests, 1337 assertions, 3 deprecations** (the 2.4.0 final report). The suite rewrites the
"generated at" timestamp in `src/Tests/MagratheaTests/test-dump/magrathea-object-test.conf`: that's
normal churn, leave it alone. Never `git stash` or `git checkout -- <file>` this tree.

Follow `plan-2.4.0.md`'s own implementation instructions for each item:

## 5f. The Query Tester `eval()`s posted code

**Error.** `src/Admin/views/actions/query-creator.php:38-64` appends `$_POST["q"]` to a PHP string
and `eval()`s it. Its page (`views/pages/query-creator.php`, "Magrathea Query Tester [WIP]") is in
the default "Database" menu (`AdminMenu` item `mag-query`, `AdminMenu.php:105,281`). Any logged-in
admin runs PHP on the server, and so does any script running in an admin's browser (see 5i).
2.4.0 made the File Editor opt-in for the same capability (item 5).

**Solution.**
- Remove the Query Tester:
  - `views/pages/query-creator.php` and `views/actions/query-creator.php`;
  - `views/javascript/query.js`. Only the Query Tester uses it; the Queries page (`db-query.php`)
    has its own inline JS and `query-run-card.php`.
- Remove the `mag-query` item from `AdminMenu::Initialize()` and from `GetDatabaseSection()`.
- `AdminMenu::Add()` ignores `null`. `GetItem()` returns `null` for an unknown key, so a custom
  `BuildMenu()` calling `GetItem("mag-query")` renders nothing instead of a broken item.
- Tests (`adminMenuTest.php`):
  - `GetDatabaseSection()` has no `mag-query`;
  - `GetItem("mag-query")` is `null`;
  - `Add(null)` adds nothing;
  - `Start::GetViewFile("pages"|"actions", "query-creator")` returns `null`.

**Impact on a 2.3.5 project.** The Query Tester page is gone (it was WIP). Links to
`?magrathea_page=query-creator` get "Page not found". A custom menu with `GetItem("mag-query")`
shows nothing there.

## 5g. Backups: shell injection, password exposure, path traversal

**Error.**
- `src/Admin/Api/DatabaseApi.php:12-25` (`CreateBackupFile()`) passes the posted `filename` to
  `AdminDatabase::GetCommand()` (`AdminDatabase.php:153-157`). That builds
  `mysqldump --opt --user=… --password=… --host=… <db> > <backups folder>/<filename>`, which
  `DoBackup()` (`:164-169`) runs with `system()`. Any logged-in admin can inject shell commands
  through the file name.
- The DB password is on the command line, so other local users see it in `ps`. It's also returned
  to the browser in `command`, which `views/pages/backups.php:83` writes with `.html()`.
- `views/actions/backup-file.php:5-6` joins `$_REQUEST["filename"]` to the backups folder
  unchecked and includes `file-view.php`, so `../` reads any file the web server can read.

**Solution.**
- New `AdminDatabase::ValidateBackupFileName(string $name): string`:
  - appends `.sql` when it's missing;
  - accepts only `^[A-Za-z0-9][A-Za-z0-9._-]*\.sql$` (no `/`, `\` or `..`);
  - anything else throws `MagratheaException("invalid file name")`.
- `DoBackup($fileName)`:
  - validates the name;
  - refuses a file that already exists (`MagratheaException("file already exists")`; mysqldump's
    `>` silently overwrote it);
  - runs `mysqldump` through `proc_open()` with an **argument array**, so no shell is involved:
    `["mysqldump", "--defaults-extra-file=<tmp>", "--opt", "--result-file=<dest>", <db name>]`.
    `--defaults-extra-file` must be the first option;
  - writes the credentials to a `[client]` temp file (`user`, `password`, `host`, `port` when set)
    created with `tempnam(sys_get_temp_dir(), …)`, `chmod 0600`, and deleted in `finally`. In
    values, backslashes are doubled and the value is quoted with `"`, or with `'` when it contains
    a `"`. A value with both quote characters, or a newline, throws `MagratheaException`;
  - on a non-zero exit code, deletes the partial file and throws `MagratheaException` with
    mysqldump's stderr;
  - throws a clear `MagratheaException` when `proc_open()` isn't available (`disable_functions`);
  - runs the process through a new protected `RunProcess(array $command): array`
    (`["code", "stdout", "stderr"]`), so tests can replace it (the `TestsManager::Execute()`
    pattern from 5d);
  - returns `["file" => <name>, "size" => <bytes>]`.
- `GetCommand()` is removed: it can only be built with the password in it.
- `DatabaseApi::CreateBackupFile()` returns `["success" => true, "file" => …, "size" => …]`, with
  no `command`. `views/pages/backups.php` drops the `#command-used` block and writes the file name
  with `.text()`.
- `views/actions/backup-file.php` reads `$_POST["filename"]` only (the page already posts) and runs
  it through `ValidateBackupFileName()`. The file must exist and its `realpath()` must be inside
  `realpath()` of the backups folder; anything else is an error card. Then it includes
  `file-view.php`, whose full mode already escapes.
- `views/actions/backups-list.php`: the `viewBackupFile(…)` `onclick` argument is built with
  `json_encode()` + `htmlspecialchars()` (the 5d pattern).
- Tests (new `src/Tests/MagratheaTests/adminBackupsTest.php`):
  - these names are rejected: `../x`, `a/b.sql`, `x;rm -rf /`, `` `id` ``, `.sql`, empty;
  - `backup_20261023` becomes `backup_20261023.sql`;
  - an existing file is refused;
  - the command array starts with `mysqldump --defaults-extra-file=…` and contains no password;
  - the temp file holds the credentials, is `0600`, and is gone after success and after failure;
  - a non-zero exit removes the partial file and throws;
  - `CreateBackupFile()`'s response has no `command`.

**Impact on a 2.3.5 project.** None, unless code calls `AdminDatabase::GetCommand()` (removed),
uses backup names with other characters (now rejected), or relies on overwriting a backup with the
same name. The web server's PHP needs `proc_open()` instead of `system()`. Hosts that disable one
usually disable both.

## 5h. `file-view` reads any file, and the log tail isn't escaped

**Error.**
- `src/Admin/views/actions/file-view.php:3-7` reads the path in `$_POST["file"]` when no including
  script set `$viewFile`. The logs page posts absolute paths (`views/pages/logs.php:73,128,138`),
  so any logged-in admin reads any file the web server can read (other apps' configs, keys). That
  bypasses the File Editor opt-in (item 5).
- The tail mode (`lines`) prints the file unescaped (`:42`). Log lines carry request data
  (URIs, user agents, posted values), so viewing a log can run script in the admin (see 5i).
- `getLastLines()` is declared as a global function inside the view, so including it twice in one
  request is a fatal "Cannot redeclare".

**Solution.**
- `file-view.php` renders only a `$viewFile` set by the script that includes it. Called directly
  (`?magrathea_subpage=file-view`, where `$viewFile` can't be set), it answers 404 "action not
  found", like an unknown action (5e).
- New action `views/actions/log-view.php` for the logs page:
  - `file` must be a plain basename (`basename($f) === $f`, no `..`, no `\`, no NUL);
  - it's resolved inside `logs_path`: `realpath()` must be inside `realpath(logs_path)` and be a
    regular file;
  - `lines` is optional, cast to int and clamped to 1–10000;
  - it sets `$viewFile` and includes `file-view.php`.
  It follows `log-delete.php`, which already takes a basename inside `logs_path`.
- The tail output is escaped (`htmlspecialchars()`), and `getLastLines()` becomes a closure, so the
  view can be included twice.
- `views/pages/logs.php` posts basenames (`$f`, not `$logPath."/".$f`) to `log-view`, for both
  view and tail.
- The path checks live in a small testable helper (e.g. `AdminFiles::ResolveInFolder($folder,
  $name)`), because the views `die()`. 5g's `backup-file.php` uses it too.
- Tests:
  - `../x`, an absolute path, a missing file and a directory are rejected;
  - a log inside `logs_path` resolves;
  - direct `file-view` without `$viewFile` gives 404;
  - a tail containing `<script>` is escaped.

**Impact on a 2.3.5 project.** None, unless custom admin code posts to `file-view` directly. Use
your own action with a fixed path, or `log-view` for logs.

## 5i. The admin renders app data as HTML (stored XSS)

**Error.**
- `src/Admin/views/elements/table.php:34` echoes every cell raw. `AdminElements::Table()` renders
  every CRUD list (`Features/CrudObject/list.php:7`), App Config, users, user logs, cache, backups,
  the Structure page and query results.
- The form templates print `$value` raw: `views/elements/form-input.php`, `form-textarea.php`,
  `form-select.php` (option values and labels, `Ref()` included), `form-date.php`,
  `form-checkbox.php`. So CRUD edit forms do too: a value with `">` breaks out of the attribute,
  and `</textarea>` out of the textarea.
- Any text an app user can store (a name, a title, a comment) runs as script in the admin of
  whoever views it, with the admin's session and CSRF token. It can then call every admin action:
  the Queries page (any SQL), and until 5f, `eval`. So a public form is one admin click away from
  code execution on the server.

**Solution.**
- `table.php`:
  - scalar values (from array rows and from models) are printed with
    `htmlspecialchars((string)$value, ENT_QUOTES)`;
  - `null` prints empty;
  - arrays and objects print as escaped JSON;
  - **values produced by a callable column (`"key" => function($row) {…}`), and callable row
    values, stay raw.** They're HTML built by the caller, who escapes the data inside (that's how
    `backups-list.php` builds its "view" link);
  - headers are unchanged (developer-provided).
- Form templates: `value` attributes, textarea content, select option values and labels
  (`Ref()` included) and checkbox values go through `htmlspecialchars(…, ENT_QUOTES)`. Labels,
  ids, classes, placeholders and attributes are unchanged (developer-provided).
- Also escaped:
  - `views/actions/query-run-card.php`: the query, the error message and the `print_r()` output;
  - `Features/UserLogs/detail.php`: the user's email and the victim;
  - `src/Bootstrap/views/actions/run-query.php`: the query, the result and the exception, where
    `$ex->getMsg()` becomes `getMessage()` (a mysqli exception has no `getMsg()`);
  - `src/Bootstrap/views/actions/show-tables.php`: names and types, with table names
    backtick-quoted in `SHOW COLUMNS FROM`.
- **Audit every in-repo caller of `Table()` and of the form elements**:
  - `Features/Cache/files.php`, `details.php` and the edit view;
  - `Features/AppConfig/list.php`;
  - `Features/User/index.php`;
  - `Features/UserLogs/latest.php`;
  - `Features/CrudObject/list.php` and `form.php`;
  - `views/pages/structure.php`, `logs.php`, `backups.php`, `demo-form.php`;
  - `views/actions/backups-list.php`, `object-detail.php`, `object-create.php`.

  Values that are meant as HTML (links, buttons, badges) become callable columns or callable row
  values. Example: `views/pages/structure.php:49,55,61,67` passes
  `"action" => "<a href=…>View</a>"` (and `$cacheLink`) as plain strings, which would print as text
  after the fix. It becomes `"action" => fn() => "<a …>"`.
  Its `"check"` values are already callables. Callers that pre-escape before passing a value (e.g.
  the Cache views from 5c) stop, or they'd show `&amp;lt;`. Report any caller that doesn't fit
  either case instead of guessing.
- Tests (new `src/Tests/MagratheaTests/adminEscapingTest.php`, output captured with
  `ob_start()`):
  - `Table()` with `<script>` in an array row and in a model row is escaped;
  - a callable column's output stays raw;
  - `null`, an int, and an array value;
  - each form element with `"><script>` as its value: input, textarea, select (value and label),
    date, checkbox;
  - `query-run-card` output.

**Impact on a 2.3.5 project.** CRUD lists and forms need nothing: they're just safe now. Custom
admin pages that pass HTML **as values** to `Table()` or to the form elements now show it as text.
Move it to a callable column (`["title" => "Edit", "key" => function($row) { return "<a
href=…>".htmlspecialchars($row["name"])."</a>"; }]`). Code that pre-escapes values for these
elements must stop, or it shows the entities. Migration section 46 has the `grep` and the example.

## 5k. Feature dispatch calls any public method over GET (added 2026-10-23, Paulo: fix)

**Error.**
- Three places call a feature method named by the query string: `views/index.php`
  (`magrathea_feature_subpage`, `$f->$subpage()`), `Start::CheckFeature()` (`magrathea_feature_action`) and
  `AdminFeature::GetPage()` (`magrathea_feature_subpage` again). `HasPermission()` returns `true` by default, and
  GET has no CSRF check.
- `AdminCrudObject::Save()` reads `$_POST["id"]` and `Assign($_POST)`: a GET (an `<img src>` in anything an
  admin opens) builds an empty model and `Save()`s it, inserting a blank row on every CRUD feature. `Delete()` runs
  with `id = null`. AppConfig's `Import()` calls `ImportData(null)` (TypeError).
- Plumbing methods (`SetObject`, `AddJs`, `__construct`, …) can be called too; they only throw or re-initialize.
- `?magrathea_feature_subpage=GetPage` makes `GetPage()` call itself until PHP runs out of stack/memory.

**Solution.**
- New `AdminFeature::IsDispatchable($method): bool`: a string matching `^[A-Za-z]\w*$` (so no `__*`), a public,
  non-static method of the feature with no required parameters, and not one of `AdminFeature`'s own methods
  (`AddJs`, `SetClassPath`, `HasPermission`, `GetMenuItem`, `IsDispatchable`, …, overridden or not), except
  `GetPage` and `Index`.
- The three dispatch points check it before `HasPermission()`; anything else answers 404 ("action not found" in
  `CheckFeature()`, a "Page not found" alert in the layout). `GetPage()` treats an empty subpage and `GetPage`
  itself as `Index()`.
- POST only (405 otherwise, the 5c `ClearCache` pattern): `AdminCrudObject::Save()`/`Delete()` (JSON error, as
  their other errors) and `AdminFeatureAppConfig::Import()`. `Import()`'s progress lines are escaped.
- Tests (new `adminFeatureDispatchTest.php`): `IsDispatchable()` for actions, plumbing, `__construct`, required
  parameters, protected/static methods, non-strings; `GetPage` with `GetPage` doesn't recurse; CRUD `Save`/`Delete`
  and `Import` answer 405 on GET and touch nothing.

**Impact on a 2.3.5 project.** None for the built-in UI (it posts). A custom feature whose action needs
arguments, or overrides an `AdminFeature` method name, isn't reachable from the URL any more (it couldn't work
with arguments anyway). Scripts calling CRUD `Save`/`Delete` or `Import` with GET get 405. Migration item 48.

## 27d. Short open tags (added 2026-10-23, Paulo: fix in 2.4.0; not a security item)

**Error.** 52 files in `src/` (about 116 tags) open PHP with `<?`, including the admin layout
(`views/index.php`), login, setup, menu and the framework's error page (`Errors/views/view-exception.php`). With
`short_open_tag=Off`, the default of PHP's recommended `php.ini-production`/`-development`, they print their code
as text: the admin doesn't render.

**Solution.** Convert every `<?` that isn't `<?php`, `<?=` or `<?xml` to `<?php` (a space added when none
follows), mechanically; `php -l` every file with `short_open_tag` off and on; a test that fails if any `src/` PHP
file still has a short open tag. Plan item 27d (Group B), changelog `**fix:**`, migration "Changes with no impact".
